### Constats

**IMPORTANT**
1. [Framework] `DepositRetryRules.java:20-27` : le calcul exponentiel fait main (1, 2, 4 min jusqu'à 1 h) n'a pas de raison écrite. Spring 7 fournit `org.springframework.util.backoff.ExponentialBackOff` (initial, multiplicateur, maximum). Le `Retry-After` n'est pas fourni par le framework, donc la fusion reste à faire. Les attentes sont en mémoire par choix (un redémarrage vaut un nouvel essai) : raison valable, mais le Javadoc ne cite pas `ExponentialBackOff`. À justifier dans le Javadoc ou à remplacer. Référence JHipster 9.4.0 : lu `AsyncConfiguration.java` de `jhipster-sample-app-websocket` (pour `@EnableScheduling`) ; JHipster n'a ni planification de réessai ni TaskScheduler programmatique. `@Scheduled` + `TaskScheduler.schedule(Instant)` + `@EventListener` sont les mécanismes Spring standard. Le `@EnableScheduling` est dans `CopyConfiguration`, pas dans une `AsyncConfiguration` comme JHipster ; antérieur à la plage, simple écart de nom.
2. [Test manquant, R-29] `RecuCopyService.java:112` (`filter(photo -> photo.getDriveFileId() == null)`). Mutation « filtre toujours vrai » : **survit**, 16 tests passent. Scénario : un reçu à deux photos, la première déposée, le dépôt de la seconde échoue. À chaque reprise la première est resoumise à Drive : appel inutile, et `photo.deposer(fileId)` sur une photo déjà déposée. Aucun test n'a un reçu à deux photos dont une seule reste à déposer. Ajouter ce cas (`r29_…`).
3. [Test manquant, R-20] `RecuCopyService.java:134` (`scheduleRetry(photo.getId(), retryRules.maximum())` pour un refus de Drive). Mutation « ligne supprimée » : **survit**. Scénario : un 403 ou 404 de Drive est réessayé immédiatement à chaque passage périodique (1 min) au lieu d'1 h. Le client est testé jusqu'à `BlockedGoogleException` (GoogleDriveClientTest:217), pas l'attente dans le service.

**MINEUR**
1. `GoogleCalls.java:48` : Drive renvoie aussi 403 `userRateLimitExceeded` pour un quota. Il est classé `FICHIER_INACCESSIBLE` (attente d'1 h) et son `Retry-After` est ignoré. Décision connue du développeur ; sans danger, la photo attend seulement plus longtemps.
2. `RecuCopyService.java:61` : la table `retries` n'est vidée que par un succès ou une autorisation accordée ; une entrée par photo en échec persistant, sans fuite significative.
3. `DefaultValuesTest` ne mentionne ni `reprise-initiale` ni `reprise-maximale`. Les valeurs par défaut (1m, 1h) ne sont pas figées par un test dédié ; les tests de rythme les utilisent indirectement via la configuration de test (non vérifié que celle-ci hérite du fichier principal).
