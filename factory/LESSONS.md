# Leçons de la factory

Retours d'expérience du premier projet (octobre 2026) qui valent pour tout projet. Chaque leçon dit ce qui s'est
passé, ce que la factory en fait, et où c'est appliqué. À relire avant un nouveau projet ; compléter à la clôture de chaque cycle.

| # | Ce qui s'est passé | Ce que la factory en fait | Où |
|---|---|---|---|
| 1 | L'architecture a changé trois fois en deux jours (hexagonale, couches, puis structure JHipster) : trois gros refactors, et le PRD et le backlog sont restés faux. | L'architecture se décide dans un ADR validé AVANT le premier code, et s'applique par des tests d'architecture dès la première issue. Elle ne change pas sans nouvel ADR. | `AGENTS.md` du modèle (section Orchestration) |
| 2 | Le PRD décrivait packages, ports et classes : il est devenu faux à chaque refactor. | Le PRD décrit le QUOI (comportement, contrats, critères), jamais le COMMENT. | `spec-writer.md` |
| 3 | Plusieurs ports n'avaient qu'une seule implémentation (stockage, dépôt, authentification, journal) : de la cérémonie sans bénéfice. | Une interface n'existe que pour une frontière externe à doubler ou avec deux implémentations réelles. | `developer.md`, `AGENTS.md` du modèle |
| 4 | Le serveur Java d'un IDE ouvert a recompilé des classes générées sans leur processeur d'annotations et cassé le build dans le dépôt (51 tests en erreur) ; chaque agent a recréé son propre script de contournement. | `scripts/verify-clean.sh` : vérification dans une copie propre, hors IDE, utilisée par tous les rôles. | `factory/scripts/` |
| 5 | Un agent a rendu un rapport réduit au mot « placeholder » ; les rapports longs consommaient le contexte de l'orchestrateur. | Format de rapport court et obligatoire ; l'orchestrateur recoupe avec `git log` et le build ; les revues sont archivées dans `docs/reviews/`. | `report-format.md`, skill `deliver` |
| 6 | Les « issues » n'étaient qu'un paragraphe du PRD : pas de statut, pas de dépendances, le backlog est resté « Spécifié » après quatre issues faites. | Une issue = un fichier avec statut, dépendances, critères, branche, commits et revue. | `docs/issues/` |
| 7 | Quatre issues et trois refactors sur une seule branche : revues énormes. | Une branche et une PR par issue ; l'utilisateur fusionne avec `--no-ff`. | `AGENTS.md` (Orchestration), skill `deliver` |
| 8 | Des missions d'agent de plus d'une heure sans point de contrôle. | Issues petites (tranches verticales), vérification de l'orchestrateur entre chaque, worktree pour les parallèles. | skill `deliver`, `to-tickets` |
| 9 | Le reviewer a dû juger à la main si des critères étaient couverts et si des tests « passés d'emblée » étaient utiles. | Le nom d'un test contient l'identifiant du critère ; `criteres-sans-test.sh` liste les critères sans test. Pour mesurer la qualité des tests, ajouter le mutation testing (voir `START-A-PROJECT.md`). | `factory/scripts/`, `developer.md` |
| 10 | Un framework a changé un contrat externe sans que les tests le voient (requêtes rejetées par un pare-feu ou le serveur avant l'application : mauvais code, aucun en-tête de sécurité). | Tests de contrat sur serveur réel (port aléatoire) dès la première issue exposant une API, y compris les requêtes malformées. | `developer.md`, `report-format.md` |
| 11 | Une dépendance ajoutée avait changé de licence (licence à usage restreint) sans que personne ne le voie. | Toute dépendance ajoutée est rapportée avec version, origine et licence ; la licence se décide avec l'utilisateur. | `developer.md`, skill `deliver` |
| 12 | Le déploiement derrière un proxy, les limites de débit et la configuration de production étaient découverts en revue. | Les prérequis de déploiement sont écrits dans `docs/deploiement.md` dès l'issue concernée. | `AGENTS.md` du modèle |
| 13 | Essai de `/deliver` sur un projet jetable (2 issues, 5 sous-agents, 3 revues) : un mineur de la revue 1 (assertion de message d'erreur trop faible) est revenu tel quel à l'issue 2, et un test de borne qui allouait 10^9 éléments bloquait au lieu d'échouer. | Un mineur qui se répète devient IMPORTANT et sa règle va dans `developer.md` ; messages d'erreur vérifiés par égalité exacte ; bornes testées par leur valeur (limite acceptée, limite + 1 refusée) ; tests de garde-fous prouvés par mutation (développeur et reviewer). | `developer.md`, `code-reviewer.md`, skill `deliver` |
| 14 | Avec des branches empilées (issue 2 créée depuis la branche non fusionnée de l'issue 1), la base `merge-base` avec la branche principale aurait fait relire les commits de l'issue 1. | La base est la pointe de la branche dont l'issue dépend. | skill `deliver` (étape 0) |
| 15 | Le PRD ne fixait pas plusieurs comportements (valeur refusée, borne, types) ; le développeur les a choisis seul, sans file d'attente pour l'utilisateur. | Rubrique « À trancher par l'utilisateur » dans le rapport du développeur, reprise par l'orchestrateur dans les Notes de l'issue et le compte rendu. | `report-format.md`, skill `deliver` |
| 16 | Les agents et l'orchestrateur ont tous réinventé les mêmes détails de poste (pas de `timeout` sous macOS, chemin absolu du projet à fournir, qui commite les fichiers d'issue). | Briefs types mis à jour, `perl alarm` documenté, l'orchestrateur commite les fichiers d'issue et de revue. | `briefs/`, skill `deliver` |
| 17 | Un agent peut orchestrer d'autres agents (essai réel) mais n'a pas d'outil pour interroger l'utilisateur, même s'il le déclare ; `spec-writer` déclarait `AskUserQuestion` sans l'avoir. | Les questions de fond au cadrage (session principale) ; `spec-writer` ne fait plus d'interview, il liste les lacunes ; l'orchestrateur reste un prompt de session principale ; un en-tête d'agent ne déclare que des outils réellement disponibles. | `spec-writer.md`, `AGENTS.md` (Orchestration), `README.md` |
| 18 | Au cadrage d'un deuxième projet, l'agent a proposé un hexagone sans relire ces leçons : l'erreur n° 1 et n° 3 a failli se répéter, et l'utilisateur l'a repérée. | Relire `factory/LESSONS.md` avant tout ADR d'architecture. | À appliquer : `AGENTS.md` du modèle, skill `grill-with-docs` |
| 19 | Un ADR proposait une seule option et annonçait trois frontières alors que ses dépendances en supposaient une quatrième. | Un ADR d'architecture compare au moins deux options et confronte le sens des dépendances aux interfaces annoncées. | À appliquer : `templates/docs/adr/0000-template.md` |
| 20 | La factory n'indiquait aucune architecture à implémenter : il a fallu reprendre à la main celle d'un projet antérieur, avec ses couches et ses règles ArchUnit. | Architecture par défaut en couches de services, avec une référence Java à adapter dans l'ADR, chaque écart étant consigné avec sa raison. | `START-A-PROJECT.md`, `AGENTS.md` du modèle, `stacks/java-maven/README.md` |
| 21 | Des reçus réels et une capture du fichier cible ont révélé tardivement des cas absents du cadrage et invalidé une hypothèse d'écriture. | Demander des exemples réels (documents, captures, fichiers cibles) dès le premier tour du cadrage. | À appliquer : skill `grill-with-docs` |
| 22 | Le dossier d'un projet a disparu un temps, cause non établie, alors que tout le cadrage n'était pas commité. | Proposer un commit dès qu'un tour de cadrage produit des fichiers, sur une branche `docs/…`. | À appliquer : skill `grill-with-docs` |
| 23 | La CI de la stack `java-maven` a échoué au premier push d'un projet, avant même l'issue socle : `setup-java` avec `cache: maven` exige un `pom.xml`, qui n'existait pas encore. | Sans `pom.xml`, les étapes Java sont ignorées et le job l'indique par une notice ; un test de la factory vérifie ces gardes. Contrepartie : un `pom.xml` supprimé par erreur donnerait une CI verte avec cette notice. | `stacks/java-maven/.github/workflows/ci.yml`, `scripts/tests/run.sh` |
| 24 | L'upgrade d'un projet Java demandait de lancer une suite de tests qui échouait forcément : 5 vérifications contrôlaient la racine du dépôt de la factory, sans Java ni Maven. L'échec, déjà présent avant l'upgrade, a dû être prouvé par comparaison avec la version précédente. | Ces vérifications ne s'exécutent que dans le dépôt de la factory, repéré par un marqueur que le test protège contre une disparition silencieuse. Une suite que les projets doivent lancer doit pouvoir y passer. | `scripts/tests/run.sh`, `.factory-depot` |
| 25 | Les agents héritaient en silence du modèle de la session : l'utilisateur a découvert en le demandant que trois agents en parallèle consommaient tous son forfait en Opus. | Modèle et effort réglables dans `.factory.conf`, et affichés par `config-factory.sh`. À mesurer : un effort faible peut suffire pour coder, à vérifier pour la revue de sécurité. | `sync-claude.sh`, `lib-config.sh`, `templates/.factory.conf` |
| 26 | Sur un projet Spring Boot annoncé « inspiré de JHipster », le développeur a recodé session, cookie et vérification du mot de passe, et deux revues centrées sur les comportements ne l'ont pas relevé : l'utilisateur l'a vu en lisant le résultat. Le code de la référence n'avait jamais été lu, et chaque correctif de revue a épaissi le code maison. | Règle « Le framework d'abord » : chercher dans la version utilisée et lire le code de la référence avant d'écrire ; tout équivalent à la main se justifie par un critère ou une mesure, dans une section du rapport contrôlée par l'orchestrateur et vérifiée par le relecteur. | `developer.md`, `code-reviewer.md`, `report-format.md`, `briefs/`, skill `deliver`, `AGENTS.md`, modèle d'ADR, `stacks/java-maven/README.md` |
| 27 | Sur le même projet, une fois la connexion reprise sur Spring, le code restait éloigné de JHipster par ses noms et sa forme, sans raison. La comparaison n'a été possible qu'en générant une application complète, et cette application ne valait que pour un projet sans frontend. | L'ADR fixe la référence et sa version. Les fichiers se lisent un par un dans les exemples publiés, selon l'authentification et le frontend. Chaque écart a une raison, dans un tableau du rapport comparé par le relecteur. | `stacks/java-maven/README.md`, `developer.md`, `code-reviewer.md`, `report-format.md`, `briefs/`, skill `deliver`, `AGENTS.md`, modèle d'ADR |
| 28 | Sur le même projet, aligner les classes sur JHipster a laissé en français celles qui n'y ont pas d'équivalent : le dossier `config` mêlait les deux langues, et aucune règle ne fixait la langue du code. L'utilisateur l'a vu en lisant le dossier. | Les classes techniques sont impérativement en anglais, règle vérifiée en revue. | `AGENTS.md`, `developer.md`, `code-reviewer.md`, `stacks/java-maven/README.md` |
| 29 | Sur le même projet, `criteres-sans-test.sh` répondait `OK` pour un critère dont le seul test avait été retiré : une Javadoc citait encore son identifiant. Le contrôle comptait toute mention, alors que son en-tête annonçait des noms de tests. | Seule une déclaration de test couvre un critère. Un contrôle préfère un faux MANQUE, visible, à un faux OK, silencieux. | `factory/scripts/criteres-sans-test.sh`, `factory/README.md` |
| 30 | Sur le même projet, la vérification de fin d'issue n'était qu'une consigne : `VERIFY OK` sortait avec 6 tests d'écran ignorés, et rien ne prouvait qu'elle avait suivi le dernier commit. | `fin-issue.sh` lie le résultat à un commit, sur arbre propre, et refuse les tests ignorés sans décision écrite. `/deliver` exige sa ligne avant `Fait`. | `factory/scripts/fin-issue.sh`, `factory/skills/deliver/SKILL.md` |
| 31 | Sur le même projet, une route a été ouverte dans une issue et sa protection reportée à la suivante ; les valeurs par défaut du framework n'avaient jamais été testées avec des valeurs hostiles. | Une entrée externe naît avec tous ses contrôles, dans la première issue qui l'ouvre, et le rapport détaille ses champs et un test hostile. | `to-tickets`, `developer.md`, `report-format.md`, `owasp-check` |
| 32 | Sur l'issue 001-02 du même projet, la revue de branche faite sans liste de mineurs a relevé trois classements et trouvé 4 constats IMPORTANT. Une seule observation. | La revue de branche finale se fait sans cette liste ; seules restent les décisions de l'utilisateur. Un risque de sécurité reporté se décide avec lui. | `deliver`, `code-reviewer.md` |
